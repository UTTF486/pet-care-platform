## 一、简历项目描述（可直接粘贴，按需删减）

> **智慧宠物服务上门平台** ｜ 个人项目 ｜ Java / Spring Boot / MyBatis / MySQL / Redis / Vue3
>
> 面向宠物上门服务场景的全栈项目，覆盖用户预约、商家履约、数据看板三条主线，独立完成需求拆解、库表设计、接口开发与前端联调。
>
> - 基于 **Redis 双 key 登录态**（token→userId、userId→用户信息）实现认证，禁用用户时可即时踢下线，避免 JWT 无法主动失效的问题
> - 设计**订单状态机**（待接单/待服务/已完成/已取消），所有流转采用 `UPDATE ... WHERE status=旧状态` 条件更新，影响行数为 0 即判定并发冲突，无需分布式锁

> - 基于 MySQL `GROUP BY DATE_FORMAT` 完成日/周/月维度报表聚合，看板接口加 60s 缓存，首页响应从多次查询降为 1 次

## 二、五条项目亮点（面试展开版）

### 亮点 1：Redis 双 key 登录态，解决"踢人下线"

**简历一句话**：Token 存 Redis 而非纯 JWT，禁用用户时可立即失效其会话。

**怎么讲**：
- 两个 key：`login:token:{token} -> userId`、`login:user:{userId} -> 用户信息 JSON`
- 请求进来先换 userId，再取用户信息；任一为空即 401
- 后台禁用用户时删掉 `login:user:{id}`，该用户下次请求立刻失效——JWT 做不到（签发即不可撤销，除非再维护黑名单）
- 每次请求刷新 TTL，实现"滑动过期"：活跃用户不掉线，闲置 2 小时才失效

**可能被追问**：Token 存 Redis 每次请求都查 Redis，性能行吗？
→ 单次 GET 在 0.1ms 级，比查库便宜得多；且 Redis 本身就是内存 KV，这正是它的定位。真正的瓶颈通常在网络往返，可加本地缓存做二级。

### 亮点 2：订单状态机 + 条件更新，不用分布式锁也不超卖

**简历一句话**：用数据库条件更新做状态机并发控制，避免"两个客服同时接同一单"。

**怎么讲**：
- 状态机只允许 5 条边：0→1、1→2、0→3、1→3、0→3(超时)
- 接单 SQL：`UPDATE t_order SET status=1, servicer_id=? WHERE id=? AND status=0`
- 影响行数 0 → 说明这瞬间状态被别人改了 → 抛"订单状态已变更，请刷新"
- 为什么不上分布式锁：锁的持有时间、续期、释放都是坑，而这里天然有一个"带行锁的更新语句"，比锁更简单可靠

**可能被追问**：如果两个人几乎同时点接单呢？
→ InnoDB 行锁会让第二个 UPDATE 等待，第一个提交后第二个的 `status=0` 条件不成立，影响 0 行，直接被拒。这就是乐观锁思想。

### 亮点 3：定时任务 + 索引，实现超时自动取消

**简历一句话**：待接单订单 30 分钟未接单自动取消，靠索引把每分钟的扫描控制在毫秒级。

**怎么讲**：
- 下单时写入 `expire_time = now + 30min`
- 每分钟 `SELECT ... WHERE status=0 AND expire_time <= NOW() LIMIT 50`
- 建了联合索引 `idx_status_expire(status, expire_time)`：等值列在前、范围列在后，符合最左前缀
- 逐单取消时仍带 `AND status=0`，防止把刚接的单误取消
- 为什么要限 50 单：避免一次任务占连接太久，剩余的下轮处理

**可能被追问**：为什么不用延时队列？
→ 单体项目引 RabbitMQ 会显著增加部署复杂度。定时扫表在十万级订单量内完全够用，延迟最多 1 分钟，业务可接受。订单量上来后我会换延迟消息或 XXL-JOB 分布式调度，并把多实例重复执行的问题一起解决。

### 亮点 4：注解式限流，业务代码零侵入

**简历一句话**：`@RateLimit(key, count, seconds)` 一个注解完成接口限流，切面用 Redis Lua 原子完成 INCR 与过期。

**怎么讲**：
- 切面取 `UserContext` 的 userId 拼 key，未登录降级用 IP
- Lua 脚本内 `INCR`，首次计数时同时 `EXPIRE`，超过阈值抛 429
- 用 Redis 而不是本地 Map：多实例部署时本地计数各算各的，等于没限
- **设计取舍**：固定窗口实现简单；更高并发可升级滑动窗口 / Sentinel

> 面试时说"我知道它有什么问题、生产会怎么改"，比说"我用了限流"高一个档次。

### 亮点 5：报表聚合下推到数据库 + 看板缓存

**简历一句话**：日/周/月三种粒度用同一套 SQL，只换 `DATE_FORMAT` 格式串；指标卡加 60 秒缓存。

**怎么讲**：
- `DATE_FORMAT(create_time, '%Y-%m-%d' | '%x-%v' | '%Y-%m')` 一个参数切换维度
- 营收只统计 `status=2`（已完成），避免把在途和已取消的金额算成收入
- 聚合交给 MySQL，不把明细捞进内存——数据量大时会 OOM
- 指标卡 60s 缓存：后台首页刷新频繁，但晚 1 分钟不影响决策

**可能被追问**：为什么不建统计表？
→ 现在数据量小，实时聚合够快；等订单到百万级会加日汇总表 + 定时任务，看板只查汇总表。这是我写在文档里的演进路径。

## 三、60 秒项目介绍（面试开场背这段）

> 这是一个宠物上门服务的预约平台，业务是从外卖系统迁移过来的：用户下单预约上门喂猫、洗澡、遛狗，商家接单派给服务师，服务完成用户评价，后台还有数据看板。
>
> 技术栈是 Spring Boot + MyBatis + MySQL + Redis，前端 Vue3 + Element Plus。
>
> 我重点做了三件事：一是订单状态机，用数据库条件更新解决并发改状态的问题；二是超时自动取消，定时任务加联合索引；三是 Redis 的三个用途——登录态、热点服务缓存、接口限流。
>
> 项目里有 9 张表、30 多个接口，代码和文档都在 GitHub 上，可以现场演示下单到完成的完整流程。

## 四、高频追问与答法

**Q1：为什么用 MyBatis 不用 JPA？**
业务查询以列表筛选、统计聚合为主，SQL 可控性更重要。MyBatis 的动态 SQL（`<if>`/`<where>`）写多条件筛选很自然，报表 SQL 也能直接优化。JPA 在复杂查询上要么写原生 SQL 破功，要么被 N+1 拖累。

**Q2：怎么防越权的？**
三层：前端路由守卫（体验）、拦截器校验角色（`/api/admin/**` 要求 role=1）、数据层 SQL 带 `user_id`（如删除宠物 `WHERE id=? AND user_id=?`）。前端拦截可被 Postman 绕过，后端才是防线。

**Q3：缓存的 key 怎么设计的？**
统一前缀分层：`cache:service:detail:{id}`、`cache:stats:overview`、`login:token:{token}`、`rate:order:create:u2`。前缀便于批量清理和排查，也能一眼看出用途。

**Q4：缓存和数据库不一致怎么办？**
用 Cache-Aside：写操作删缓存而不是更新缓存。并发写时"更新缓存"可能把旧值覆盖上去，删除更安全。删除后下次读回源，容忍窗口很短。极端情况需要延迟双删或 binlog 订阅，本项目规模不需要。

**Q5：`@Transactional` 有哪些坑？**
三个：① 默认只回滚 `RuntimeException`，受检异常要写 `rollbackFor = Exception.class`；② 同类内部方法调用不走代理，事务失效；③ 事务里做远程调用/发消息会拖长事务，应放到事务提交后（`TransactionSynchronization`）。本项目消息入库和业务在同一事务，是因为它只是本地 INSERT，不涉及外部系统。

**Q6：为什么不用 PageHelper？**
少一个依赖，且分页逻辑透明：`count` 一次 + `limit` 一次。面试官问分页原理时，能直接指着 SQL 讲，而不是"框架帮我做的"。

**Q7：订单表为什么要存服务名和价格？**
快照。商家改价改名后，历史订单不能跟着变，否则对账和纠纷都说不清。同理 `sales` 是冗余字段，用一致性换查询性能，在完成订单的同一事务里 `+1`。

**Q8：如果要做支付，怎么改？**
加"待支付"状态和支付超时关单：下单生成待支付订单 → 调支付 → 回调里改状态（回调必须幂等，用订单号 + 状态条件更新）→ 超时未支付走关单任务。金额要在服务端二次校验，回调要验签。

**Q9：项目最难的地方？**
状态机的并发控制。一开始我是"先 SELECT 判断状态，再 UPDATE"，自测时用两个线程同时接单，两个都成功了。后来改成条件更新，用影响行数判断，才彻底解决。这个坑让我理解了"检查与执行之间存在时间窗"这件事。

**Q10：如果重做，你会改什么？**
① 定时任务加 Redis 锁，支持多实例；② 限流升级滑动窗口 / Sentinel；③ 前端状态管理从 localStorage 换成 Pinia；④ 增加状态机与业务服务的集成测试——目前已有 Mapper XML 和分页边界自检，业务测试仍需补强。

## 五、演示注意事项

1. **先开 Redis 再开后端**，否则首页热门服务会降级查库（能跑但日志有 warn）
2. 演示顺序：看板 → 用户下单 → 催单 → 后台接单 → 完成 → 评价 → 回看板数据变化
3. 提前把 `timeout-minutes` 改成 1，当场演示超时自动取消（等 1~2 分钟，别让面试官干等，可以先讲别的）
4. 别演示"删库重建"，风险高且没意义
5. 准备一个"已知不足"清单（见 Q10），被问到时坦然承认，比硬撑好
