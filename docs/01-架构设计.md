# 01 · 架构设计

## 1. 整体结构

单体分层架构，前后端分离。当前业务规模不拆微服务，避免为小规模系统引入额外的部署、链路追踪和一致性问题。

```
┌──────────────────────────────────────────────────────────────┐
│                         浏览器                                │
│   用户端 /user/**            商家后台 /admin/**                │
│   Vue3 + Element Plus + ECharts + Axios                       │
└───────────────────────────┬──────────────────────────────────┘
                            │ HTTP /api/**（JSON）
                  ┌─────────▼──────────┐
                  │  Vite devServer    │  开发期反向代理，消除跨域
                  │  proxy → :8080     │
                  └─────────┬──────────┘
┌───────────────────────────▼──────────────────────────────────┐
│                     Spring Boot 单体                          │
│                                                              │
│  ① 接入层    AuthInterceptor（登录态 + 角色校验）              │
│              RateLimitAspect（AOP 限流）                      │
│              GlobalExceptionHandler（统一异常出口）            │
│                                                              │
│  ② 控制层    Controller × 10（用户端 5 个 / 后台 5 个）        │
│              只做参数接收、调用 Service、包装 Result           │
│                                                              │
│  ③ 业务层    Service（7 个）                                  │
│              事务边界、状态机校验、权限判断、缓存读写           │
│                                                              │
│  ④ 持久层    Mapper 接口 + XML（9 组）                        │
│              动态 SQL、关联查询、统计聚合                      │
│                                                              │
│  ⑤ 调度       OrderTimeoutTask（每分钟扫超时单）              │
└──────────┬────────────────────────────────┬──────────────────┘
           │                                │
    ┌──────▼──────┐                  ┌──────▼──────┐
    │   MySQL 8   │                  │    Redis    │
    │  9 张业务表  │                  │ 登录态/缓存/限流 │
    └─────────────┘                  └─────────────┘
```

## 2. 分层职责与约束

| 层 | 允许做 | 禁止做 |
| --- | --- | --- |
| Controller | 参数校验（`@Valid`）、调用 Service、包装 Result | 写业务判断、直接调 Mapper |
| Service | 事务、状态机、权限、缓存、组装 VO | 感知 HttpServletRequest |
| Mapper | 一条 SQL 一件事 | 写业务分支 |
| Task | 触发 Service 的批处理方法 | 在任务里直接写 SQL |

**为什么 Service 不能感知 Request**：这样定时任务、单元测试、未来的 MQ 消费者都能复用同一段业务逻辑。`OrderService.cancelTimeoutOrders()` 就是被定时任务复用的例子。

## 3. 关键链路

### 3.1 下单

```
前端校验表单
  → POST /api/orders
  → AuthInterceptor：Token → Redis → LoginUser → ThreadLocal
  → RateLimitAspect：可信代理解析客户端 IP + Redis 计数
  → OrderService.create()  【@Transactional】
       1. 按 requestId 幂等预查，再锁定宠物行校验归属
       2. 校验服务存在且已上架
       3. 计算 appointment_start/end，按服务时长生成时间区间快照
       4. 金额 = 服务单价（前端传的金额一律丢弃）
       5. 生成订单号和超时时间，INSERT t_order
       6. 唯一键 uk_user_request 兜底并发重复；uk_order_no 冲突自动换号重试
       7. INSERT t_order_log（0 → 0，用户提交预约）
       8. INSERT t_message（通知用户和商家信箱）
     ↑ 1~8 任一失败全部回滚
  → 返回 OrderVO（含宠物名、服务封面等关联字段）
```

**关键设计**：金额不在前端计算。哪怕前端被改，后端也只认数据库里的 `price`，并把当时的 `service_name`/`service_price` 写进订单做快照。

### 3.2 接单（后台"审核"）

```
PUT /api/admin/orders/{id}/accept?servicerId=1
  → AuthInterceptor：/api/admin/** 且 role != 1 → 403
  → OrderService.accept()
       1. 校验订单存在、status == 0
       2. SELECT ... FOR UPDATE 锁定可接单服务师
       3. 锁定读检查该服务师时间区间是否与已有待服务订单重叠
       4. UPDATE t_order SET status=1, servicer_id=?, accept_time=NOW()
          WHERE id=? AND status=0        ← 条件更新，影响行数=0 就抛异常
       5. 服务师接单数 +1
       6. 写日志 + 通知用户
```

### 3.3 超时自动取消

```
@Scheduled(cron = "0 * * * * ?")  每分钟
  → Redis SET NX 获取单实例锁
  → SELECT * FROM t_order WHERE status=0 AND expire_time <= NOW() LIMIT 50
        （走 idx_status_expire 索引，不全表扫）
  → 逐单 UPDATE ... WHERE id=? AND status=0
        影响行数=0 说明刚被接单，跳过
  → 写日志（operator_type=2 系统）+ 通知用户
```

每单通过独立 Bean 的 `REQUIRES_NEW` 事务处理；单条失败只记录日志并继续其他订单。
Redis 锁只减少多实例重复扫描，订单状态条件更新仍是最终并发防线。

### 3.4 数据看板

```
GET /api/admin/stats/overview
  → 先读 cache:stats:overview（TTL 60s）
  → 未命中：
      今日/累计：同一条 SQL，start 传不传决定范围
      好评率 = rating>=4 的条数 / 总条数
      待接单数 = count(status=0)
  → 回写缓存
```

报表聚合全部下推到 MySQL（`GROUP BY DATE_FORMAT`），不把明细捞到内存里算。

## 4. 订单状态机

```
                  ┌───────────────┐
        下单       │  0 待接单      │
       ──────────▶ │               │
                  └──┬─────────┬──┘
            商家接单 │         │ 用户取消 / 商家拒单 / 超时
                     ▼         ▼
                  ┌───────────────┐      ┌───────────────┐
                  │  1 待服务      │─────▶│  3 已取消      │
                  └──────┬────────┘ 取消  └───────────────┘
                  完成    │
                          ▼
                  ┌───────────────┐
                  │  2 已完成      │──▶ 可评价（一单一评）
                  └───────────────┘
```

**只有这 5 条边是合法的**，其余状态跳转全部拒绝。校验集中在 `OrderService`，不散落到各处。

**并发安全**：不依赖分布式锁，靠 `UPDATE ... WHERE status = 旧状态` 的条件更新。数据库行锁天然串行化，影响行数为 0 即视为"状态已被别人改过"。这是本层最值得讲的点。

## 5. Redis 使用一览

| Key | 类型 | TTL | 用途 | 失效策略 |
| --- | --- | --- | --- | --- |
| `login:token:{token}` | String | 2h | Token → userId | 登出只删当前 token；每次请求续期 |
| `login:user:{userId}` | JSON | 2h | 用户信息，免查库 | 禁用用户时删除（即刻踢下线） |
| `cache:service:hot` | JSON | 10min | 热门服务列表 | 服务增删改时全清 |
| `cache:service:detail:{id}` | JSON | 30min | 服务详情 | 同上 |
| `cache:stats:overview` | JSON | 60s | 看板指标卡 | 自然过期（允许 1 分钟延迟） |
| `rate:order:create:u{id}` | String | 60s 窗口 | 下单限流计数 | 自然过期 |
| `urge:order:{id}` | String | 5min | 催单去重 | 自然过期 |

**缓存模式**：Cache-Aside。读：缓存 → 未命中查库回写；写：**删缓存**而非更新缓存。

> 为什么删而不是更新：两个并发写请求，先到的可能后写缓存，把旧值盖上去。删除是"标记失效"，下次读自然回源，容忍脏读的时间窗更小。
>
> 已知缺陷：删缓存与更新数据库非原子，极端情况仍会读到旧值。彻底解决要上 Canal 订阅 binlog 或延迟双删，本项目规模不需要。

## 6. 限流设计

```java
@RateLimit(key = "order:create", count = 5, seconds = 60, message = "下单太频繁了…")
```

切面逻辑：Lua 脚本原子执行 `INCR key`，首次计数同时 `EXPIRE 60s`；若 > count 抛 429。

- **按用户维度**：`rate:order:create:u2`，未登录降级按 IP
- **为什么用 Redis**：多实例部署时本地 Map 各算各的，拦不住
- **故障策略**：公开浏览接口 `failOpen=true`，Redis 故障时降级查库；登录、注册、改密 `failOpen=false`，安全校验不可用时拒绝请求。
- **实现**：`INCR` 与 `EXPIRE` 合并到同一个 Lua 脚本，避免进程在两步之间中断导致 key 永久保留：

```lua
local current = redis.call('INCR', KEYS[1])
if current == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
return current
```

固定窗口仍是简单的近似流控；并发更高时可升级滑动窗口或接入 Sentinel。

## 7. 权限模型

只分两个角色，用 `t_user.role` 区分（0 普通用户 / 1 商家管理员），不引入 RBAC 五张表——需求里没有"多角色细粒度权限"，硬做就是过度设计。

校验分三层：

1. **前端路由守卫**：体验层，未登录跳登录页，非管理员不能进 `/admin`
2. **后端拦截器**：`/api/admin/**` 校验 `role == 1`，这是真正的门
3. **数据层隔离**：写操作 SQL 带 `user_id = 当前用户`，防越权（如 `DELETE FROM t_pet WHERE id=? AND user_id=?`）

> 前端拦截只能改善体验，不能作为安全边界；请求可绕过页面直接调用，后端校验才是最终防线。

## 8. 事务边界

| 操作 | 是否事务 | 理由 |
| --- | --- | --- |
| 下单 | ✅ | 订单 + 日志 + 消息必须同生共死 |
| 接单/完成/取消 | ✅ | 状态变更 + 日志 + 消息 |
| 查询列表/详情 | ❌ | 只读，加事务浪费连接 |
| 统计报表 | ❌ | 多表一致性要求低，允许短暂不一致 |

统一用 `@Transactional(rollbackFor = Exception.class)`，因为 Spring 默认只回滚 `RuntimeException`，受检异常不会回滚——这是新手高频踩坑点。

## 9. 风险与演进

| 风险 | 现状 | 生产方案 |
| --- | --- | --- |
| 定时任务多实例重复执行 | 单机 | Redis 分布式锁 / XXL-JOB 调度中心 |
| 扫表取消不够精确 | 每分钟一批，最多延迟 1 分钟 | 延迟消息（RocketMQ 延迟等级 / Redis ZSet） |
| 缓存穿透 | 不存在的 id 每次查库 | 空值缓存 + 布隆过滤器 |
| 缓存击穿 | 热点 key 过期瞬间打库 | 互斥锁重建 / 逻辑过期 |
| 缓存雪崩 | TTL 集中 | TTL 加随机抖动 |
| 报表慢查询 | 单表扫描 | 按 `create_time` 预聚合到日表 |
| 无支付 | 下单即生效 | 接入支付 + 待支付状态 + 关单 |
| 无监控 | 只有日志 | Actuator + Prometheus + 告警 |
