# 02 · 数据库设计

## 1. 实体关系

```
t_user 1 ──── n t_pet                 一个用户多只宠物
t_user 1 ──── n t_order               一个用户多个订单
t_category 1 ── n t_service           一个品类多个服务
t_service 1 ── n t_order              一个服务被多次下单
t_pet 1 ──── n t_order                一只宠物多次服务
t_servicer 1 ─ n t_order              一个服务师接多单（未接单为 NULL）
t_order 1 ─── 1 t_review              一单一评
t_order 1 ─── n t_order_log           一单多次状态流转
t_user 1 ──── n t_message             用户消息（user_id=0 为商家信箱）
```

## 3. 关键字段设计取舍

### 3.1 订单表冗余 `service_name` / `service_price`

**问题**：订单能不能只存 `service_id`，展示时 JOIN 服务表？

**不能**。商家改价、改名后，历史订单金额会被"篡改"。交易类系统必须快照：

```sql
service_id     BIGINT        -- 关联，用于统计
service_name   VARCHAR(64)   -- 下单时的名称快照
service_price  DECIMAL(10,2) -- 下单时的单价快照
amount         DECIMAL(10,2) -- 实付金额（未来有优惠券时 ≠ 单价）
```

同理 `t_service.sales` 是销量冗余：首页按销量排序，若每次都 `COUNT(t_order)` 会拖垮列表页。代价是要在"完成订单"时同步 `+1`，一致性靠同一事务保证。

### 3.2 金额一律 `DECIMAL(10,2)`

不用 `FLOAT/DOUBLE`——浮点二进制无法精确表示 0.1，累加会出现 `0.30000000000000004`。金额计算必须是精确十进制。

### 3.3 状态用 `TINYINT` 而非字符串

`status TINYINT` 存 0/1/2/3，比 `VARCHAR('PENDING')` 省空间、比较快。可读性靠常量类 `OrderStatus` 和 SQL 注释弥补。

### 3.4 逻辑删除还是物理删除

本项目：**宠物档案物理删除，订单永不删除**。

- 宠物：用户自己删的数据，且订单里已存 `pet_id`，即使档案没了也不影响历史订单展示（订单列表 JOIN 是 LEFT JOIN，`pet_name` 为空也不报错）
- 订单：涉及金额与纠纷，只能取消（status=3），不允许物理删除

企业项目更常见的做法是加 `is_deleted` 逻辑删除，好处是可恢复、可审计，代价是每条 SQL 都要带 `is_deleted = 0`，容易漏。本项目为了 SQL 简洁没上，面试被问要能答出这个取舍。

### 3.5 为什么不用物理外键

`FOREIGN KEY` 会带来：插入顺序约束、级联操作不可控、分库分表后失效、高并发下额外的锁开销。

业界普遍做法是**应用层保证引用完整性** + 必要索引。项目里通过 Service 层校验（如"宠物必须属于当前用户"）来保证，并把 `pet_id` 等字段建成普通索引。

## 4. 索引设计

| 表 | 索引 | 支撑的查询 |
| --- | --- | --- |
| `t_user` | `uk_username` | 登录查账号；唯一约束防并发重复注册 |
| `t_pet` | `idx_user_id` | 我的宠物列表 |
| `t_service` | `idx_category_status` | 首页按品类 + 上架状态筛选（最左前缀：只传 status 时用不上，但列表页几乎总带品类） |
| `t_order` | `uk_order_no` | 订单号查询 + 防重复 |
| `t_order` | `idx_user_status(user_id, status, create_time)` | 我的订单（带状态筛选 + 按时间倒序，覆盖 WHERE + ORDER BY） |
| `t_order` | `idx_status_expire(status, expire_time)` | 定时任务扫超时单，**避免每分钟全表扫** |
| `t_order` | `idx_create_time` | 报表按时间范围聚合 |
| `t_review` | `uk_order_id` | 一单一评，数据库层防重复提交 |
| `t_message` | `idx_user_read(user_id, is_read)` | 未读数统计 |

**联合索引顺序的考虑**：`idx_status_expire` 把区分度低但必带的 `status` 放最左，`expire_time` 放右侧做范围扫描——因为定时任务的 SQL 是 `status = 0 AND expire_time <= NOW()`，等值在前、范围在后，符合最左前缀原则。

**`idx_user_status` 把 `create_time` 放第三位**：`WHERE user_id=? AND status=? ORDER BY create_time DESC` 可以完全走索引，避免 filesort。

## 5. 用唯一索引做幂等

这是本项目最容易被忽略但很实用的设计：

| 场景 | 手段 |
| --- | --- |
| 并发重复注册 | `uk_username`，第二个请求直接抛 `DuplicateKeyException` |
| 重复评价 | `uk_order_id`，即使前端连点也只会成功一次 |
| 重复订单号 | `uk_order_no`（时间戳 + 4 位随机，碰撞概率极低但仍需兜底） |

> 先 `SELECT` 判断再 `INSERT` 存在竞态窗口（检查后、插入前被别人插入）。唯一索引是数据库层的最终防线，应用层的预查询只是为了给用户友好提示。

## 6. 数据量增长后的演进

| 阈值 | 动作 |
| --- | --- |
| `t_order` 百万级 | 报表改为按日预聚合到 `t_order_stat_daily`，看板不再扫明细 |
| `t_order` 千万级 | 按 `create_time` 月分表，或按 `user_id` 哈希分库 |
| `t_order_log` 膨胀 | 冷数据归档到历史表 / OSS |
| 消息表 | 已读超过 30 天的批量清理 |

现在不做，是因为数据量没到——**过早优化是另一种不专业**。面试时说清"什么量级做什么决策"比堆方案更有说服力。

## 7. 初始化

```bash
mysql -uroot -p < sql/pet_service.sql
```

脚本包含：
- 9 张表 DDL（含注释，可直接当文档看）
- 种子数据：4 个账号、4 只宠物、4 个品类、8 个服务、4 位服务师、8 笔分布在最近 7 天的订单、5 条评价、3 条消息

种子订单的意义：**看板一打开就有图**，不用先手工造数据才能演示。
